# Решения

## 2026-11-22 — WeChat не грузит медиа при прямом пути

Симптом у всех клиентов, мобильная сеть и Wi-Fi, любые версии Happ: WeChat открывается, текст местами приходит, файлы и медиа почти не грузятся. Через чужой нероссийский VPN работает. Клиентский профиль не менялся с 11.09.2026.

Решение владельца: WeChat остаётся напрямую. Туннель для WeChat отклонён: теряется скорость.

H1 и H2 не исключают друг друга: при подмене DNS телефон получает чужой узел, и прямой путь к нему может попасть под заморозку. Правка DNS помогает только при живом прямом пути до правильного узла.

### Выбор правки (если проверка подтвердит H1)

Две DNS-записи WeChat: обычный UDP заменить на DoH по IP у тех же провайдеров (DNSPod 1.12.12.12, AliDNS 223.5.5.5) или на TCP. Запрос идёт напрямую. Маршрутизация WeChat не меняется.

- Обратимо: откат одной командой на мосту, профиль строится на каждый запрос `/sub` (×2).
- Документация Xray описывает DoH по IP и TCP-режим (×3).
- Не касается ключей, портов, DNAT, сервера выхода. Текущие подключения не рвутся.
- Худший исход: DoH заблокирован → срабатывают следующие серверы, как сейчас при отказе UDP.

Порог: правка только после проверки на мосту. Если скачивание с узла из настоящего ответа DNSPod встаёт на первых килобайтах — H2, правка DNS не поможет, стоп и доклад владельцу.

### Результат и пересчёт

- Мост: китайские DNS отвечают настоящими адресами по UDP, TCP и DoH; скачивание с CDN Tencent ~3 МБ/с без заморозки. Путь телефона через оператора мостом не воспроизводится.
- Правка DoH выложена (`31d1f41`), телефон владельца забрал подписку после выкладки. WeChat без изменений.
- Причина неудачи: под Happ DNS приложений задаёт «Tunnel DNS» самого Happ, в JSON провайдера он не попадает (документация Happ, Routing → JSON-подписки). Секция `dns` профиля действует только на собственные запросы Xray. Правка не могла повлиять на адреса, к которым подключается WeChat.
- H1 (DNS профиля): P 0.28 → ~0.05, отброшена в нашей формулировке.
- Найдено попутно (документация Xray: sniffing, `IPIfNonMatch`): правило по домену срабатывает, только если домен виден. Соединения WeChat по голому IP уходят в каскад. WeChat у нас частично напрямую, частично через выход. Замером не подтверждено.
- Правка DoH оставлена: на работу клиентов не влияет, откат ничего не даёт.
- Следующая решающая проверка: WeChat на телефоне с выключенным Happ. Грузит — прямой путь жив, искать в Happ (Tunnel DNS, разделение трафика WeChat). Не грузит — режет оператор (H2), решение о пути WeChat за владельцем.

### Проверка H7: ответы Tencent из России и из Эстонии

Запрос к DNS Google с подсетью клиента: Россия 95.24.0.0/16, Эстония 90.190.0.0/16 (страны по RIPEstat). Домены WeChat: `szextshort.weixin.qq.com`, `vweixinthumb.tc.qq.com`, `wx.qlogo.cn` — одинаковые наборы адресов. `dldir1.qq.com`, `mmbiz.qpic.cn` — разные адреса из тех же сетей Tencent. «Эстонский» адрес `dldir1.qq.com` — тот же, с которого мост качал ~3 МБ/с.

H7: ×0.1 → ~0.1, отброшена. DNS не причина, конфиг работает (замечание владельца подтверждено).

Остаётся: без Happ WeChat работает; через чужой VPN работает; наш профиль не менялся с 11.09; в ноябре Happ переделал DNS и туннель (выпуски Android/Desktop 06–20.11); документация Happ: «Анализ пакетов (Sniffing) может влиять на загрузку медиа в приложении WeChat». Вероятная область причины — клиент Happ. Механизм не установлен.

### Итог 22.11.2026

Владелец уточнил: WeChat одинаково плохо грузит медиа и с Happ, и без него. Через чужие зарубежные VPN работает. Откат правки DoH владелец отклонил.

Вывод: причина внешняя — прямой путь из России до серверов Tencent у операторов (H2 возвращается). Наш конфиг и Happ её не создают. Проверка с моста (датацентр) путь операторов не воспроизводит. Механизм (заморозка сетей ТСПУ, проблемы на стороне Tencent) не установлен.

Варианты — решение владельца: ждать восстановления прямого пути; или пустить WeChat через туннель (работает у чужих VPN, но владелец против из-за скорости).

Проверка владельца: ссылка `vless://` на эстонский выход (direct, без моста и без правил — весь трафик через выход) — WeChat грузит. Путь через наш выход рабочий.

### Решение владельца: развивать DNS, WeChat напрямую

Интернет (detector404, info24) и Grok: массовые жалобы на медиа WeChat в России с 19–20.11.2026. Замер: для подсети США Tencent отдаёт для медиа другие сети, чем для России и Эстонии.

Сделано: режим `dns_from_json` только для отмеченного клиента. Подписка велит Happ брать DNS туннеля из профиля, профиль перехватывает эти запросы в DNS-модуль Xray, домены WeChat резолвятся Google DoH с подсетью США. Маршруты не меняются. Перехват не сработал — DNS идёт на 8.8.8.8 через туннель, как сейчас. Откат для клиента — снять отметку. Шанс невысокий: проблема общая для России, ECS «иногда даёт другие узлы» (Grok).

Проверка владельца: ссылка `vless://` cascade (через мост на тот же выход, без правил) — WeChat **не грузит**. Разница — участок через мост: телефон → выход работает, телефон → мост → выход нет. Причина на мосту или на участке мост → выход не установлена. Следующие проверки: скорость (fast.com) по обеим ссылкам; на мосту — заполнение conntrack и правила iptables для порта выхода.
